# Query catalogue

CompanyBench 2.0.0 contains **250 public-web company searches**, plus **12 separate
development examples**. It is an authored breadth catalogue, not a random sample of
GTM demand or observed customer query logs. Query complexity and industry are
deliberately varied; the overall result describes this catalogue's composition.

The canonical records, release metadata, provenance ledger, and retired records
are packaged under `src/companybench/data/`. JSONL is authoritative; CSV, JSON and
XLSX are exports. The metadata records the original catalogue's SHA-256 and release
errata. No actual provider ranking or human audit is implied by these files.

## Release contents

The release retains 225 public cases from the original catalogue. CSB-096 through
CSB-120 required CRM, consented events, product analytics, or licensed intent data;
they are preserved as retired records and are not selectable in the default
public benchmark. Their IDs are never reused.

New cases CSB-251 through CSB-275 add ten simple searches in less represented
industries/geographies, ten bounded public cohorts, and five public event searches.
The 250 active cases have one-based release indexes independent of their stable
IDs. Index 100 is therefore not CSB-100. Exports and the CLI show both values.

Complexity is a descriptive annotation, not a measured difficulty score:

| Class | Saved code | Meaning | Cases |
|---|---|---|---:|
| Basic filters | L1 | Straightforward industry, location or company-type requirements | 27 |
| Multiple requirements | L2 | Several filters or a specific business description | 71 |
| Specific evidence | L3 | Dated events, numeric thresholds, specialist facts or relationships | 118 |
| Complex conditions | L4 | Combined relationships, event sequences or difficult exclusions | 34 |

The results website displays these class names. Saved datasets, CLI selections
and URL filters retain the release codes for compatibility with existing runs.

Every case has exactly one `primary_category`: firmographic, semantic,
technographic, signals, ecosystem, or finite_reference. Other facets overlap
freely: industry, geography, family, filters, signals, topic tags, and verification
method. Topic tags distinguish AI vendors (`ai_companies`) from companies adopting
AI (`ai_adoption`). These tags describe the explicitly authored case, not a guess
about every returned company's business.

## Acceptance and evidence

Retained cases preserve the original query and acceptance wording together in a
single semantic condition. This intentionally preserves nested alternatives,
exclusions, quantitative thresholds, and event ordering. Automatically splitting
sentences on “and” or “or” could change their meaning. New cases have separately
authored conditions where appropriate. Criteria are not generated by an LLM at
execution time.

The query, acceptance interpretation, company unit, and criterion descriptions
form the search contract. No missing source, blocked page, or failed technology
detector proves a company fails a requirement. A company must have affirmative
evidence for every required condition to receive verified credit. Ranges are
inclusive. Rolling date windows mean `(reference_time - N days, reference_time]`;
event dates and announcement dates are different unless the case specifically
asks for an announcement.

Website-technographic cases explicitly identify public HTML evidence. CSB-198
requires public coordinates and a documented straight-line distance calculation.
A researcher that cannot obtain these forms of evidence must preserve the gap.
All open-ended cases retain `satisfiability="unverified"` and an unknown expected
count: catalogue inclusion does not promise 50 matching companies exist.

## Exhaustive reference cohorts

Only CSB-261 through CSB-270 have exhaustive references. Each query names a
historically fixed, fully enumerated cohort published by its responsible public
authority: regulatory designations, procurement recipients, licence awards,
competition shortlists, approvals, awards, or a bounded patent-filing ranking.
Each reference records its source, date, complete names, aliases, and exact scope.
These are factual historical memberships checked against the cited official
announcement, not an assertion of exhaustive knowledge of the wider industry.

Historical entities remain separate where the query requires them, even if they
subsequently merged. Company domains are identity locators; a domain match alone
does not prove that a parent or successor was the historical recipient. Evidence
must establish the named company. Correct lists can have fewer than the requested
50 results, so these cases use their known eligible universe for true recall.

**Do not send reference answers, expected counts, source-provenance notes, or
scoring metadata to search providers.** The query may name an authority or dated
cohort because that is a realistic search constraint; its answer key remains
evaluation-only.

## Selection and custom datasets

```python
from companybench.datasets import load_dataset, select_queries, export_dataset

queries = load_dataset()
subset = select_queries(
    queries,
    where=['industry == "Manufacturing"', 'complexity in ["L1", "L2"]'],
    sample=5,
    seed=42,
)
export_dataset(subset, "manufacturing.jsonl")
development = load_dataset("development")
```

Explicit IDs, indexes, and inclusive index ranges are unioned first. Repeated
filters and named segments then intersect that set; seeded sampling happens last
without replacement. Results retain catalogue order. An invalid ID, out-of-range
index, duplicate selector, unknown field, or oversized sample fails clearly.
Zero-size samples and empty filter results are allowed.

Named segments are `simple`, `complex`, `technographic`, `ai_companies`,
`ai_adoption`, `manufacturing`, `signals`, and `finite_reference`. Filter expressions
support `and`, `or`, `not`, equality/inequality, ordering, and `in`/`not in` over
literal lists or field values. For example, `"ai_companies" in tags`.
Expressions are parsed through an allowlisted AST; function calls, attribute
access, comprehensions, imports, and arbitrary execution are rejected.

Custom JSONL/JSON may add scalar or list metadata fields for filtering. JSON may
contain either a list of queries or an object with a `queries` list. A trusted
Python module can expose a function returning `Query` instances or equivalent
dictionaries and be loaded with `load_dataset("my_module:cases")` or
`load_dataset("./my_queries.py:cases")`. The factory is invoked as `cases()` with
no arguments, unlike provider factories (`**options`) and judge factories
(`options={...}`). Python files support dataclasses and are imported under an
identity that includes their source-content hash. Python plugins execute local
code and must be trusted. Development examples are separate authored prompts and are excluded
from default selection.

When contributing, supply the complete acceptance logic, public evidence method,
identity unit, time semantics, facets, and provenance. Set `reference.exhaustive`
only when a cited authority establishes the entire precise eligible set. An
example list, provider result union, or sample of known matches is non-exhaustive.
Release any wording or reference correction with a revision and an erratum;
recompute affected reports instead of silently changing published results.

XLSX export requires the `excel` extra. Nested fields use JSON inside CSV/XLSX
cells. Spreadsheet exports store text safely instead of executing leading
formula characters; JSON/JSONL retain the canonical text exactly.
